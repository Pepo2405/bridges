## Recommended order & dependency notes

Suggested sequence: **001 → 002 → 003 → 004**, then 005/006/007 in any order, then
the P3 direction items (008/009) as appetite allows.

- **001 (XSS) first** — it's the only RCE-class issue; team-shared notes execute
  arbitrary JS today. Severity over everything else.
- **002 next** — tiny fix, closes a forgeable audit trail; clean server-test verification.
- **004 depends on 003** — the CI workflow runs the client test suite, which 003
  creates. 004's server-test and typecheck steps work without 003; the client-test
  step is guarded so the workflow is valid either way.
- **009 soft-depends on 003** — its `parseHeadings` unit test needs the Vitest
  runner from 003; without it, fall back to the manual editor check. 009's Step 1
  (README correction) is independent and shippable alone.
- **008 depends on external code-signing** — the Tauri updater needs signed update
  artifacts; the spike must resolve signing + private-repo hosting before any rollout.
- **Deferred (no plan, by design):** extracting the sync engine out of the
  `store.ts` / `App.tsx` god-files is real tech-debt but **MED-risk and must wait
  until 003 gives the sync engine test coverage**. Do not refactor `store.ts`
  before characterization tests exist.

## Findings considered and rejected (so they aren't re-audited)

- **CORS `Access-Control-Allow-Origin: *`** (`server/src/index.ts:37-40`) — not
  exploitable: auth is bearer-token, not cookies, so cross-origin requests don't
  carry credentials. By-design for a self-hosted multi-origin tool.
- **Path traversal** (`server/src/vault.ts:resolveInVault`, Rust
  `lib.rs:resolve_in_vault`) — both are correctly guarded (containment check /
  component-by-component rejection of `..`/root/prefix). No bypass found.
- **"Unbounded request body DoS"** — Bun's `Bun.serve` caps request bodies at
  128 MB by default; not unbounded. Optionally lowerable, but not a real DoS.
- **SSE `?token=` query param** (`server/src/index.ts:69`) — accepted but **no
  client actually sends it** (both the Rust desktop SSE and the browser-mode
  `fetch` use the `Authorization` header). Latent only; documented in README.
- **Preview re-render per keystroke** — Solid's lazy `createMemo` + the edit/preview
  mode gating mean `preview()` (marked.parse) does **not** recompute while typing.
- **applyDocs echo race** (`store.ts:157-191`) — suppressed by the 400 ms watcher
  debounce + the `synced_hash` equality check in `enqueuePush`.
- **SSE generation-counter race** (Rust `start_event_stream`) and **SessionRuntime
  coupling** — examined; not real issues.
- **`bumpSeq` unawaited `stateSave`** (`store.ts:879`) — real but LOW impact:
  `reconcile(sync 0)` on boot is the source of truth, so a missed `last_seq`
  persist only causes a redundant pull, not data loss. Not worth a plan.
- **Wikilink autocomplete "missing"** — actually **already implemented**
  (`MarkdownEditor.tsx`). The README backlog entry is stale; plan 009 corrects the
  doc and adds the genuinely-missing heading-level completion instead.
- **Server lockfile** — server has zero npm deps by design (Bun stdlib only);
  reproducibility isn't at risk until a dependency is added.

## Performance note

All performance findings (full-vault re-hash on every SSE reconnect; per-sync
`buildBacklinks`/`buildTree`; GraphView rebuilds) are real but **fine at the
current ~70-doc scale** and degrade only past several hundred docs. Not planned
now; revisit if vault sizes grow. The one with the best near-term cost/benefit is
debouncing `reconcile()` on rapid reconnects (`store.ts:776,704`) — noted here so
it isn't lost.
